# 四个实验站点选题分析

> 更新时间：2026-09-12
>
> 本文解释本次新增 4 个静态 MVP 的选择逻辑。它们是独立实验，不代表已经验证了市场需求、收入或搜索排名。

## 1. 总体选择方法

这次没有继续追逐更多泛热点，而是从前一轮搜索信号中挑选能被做成“具体任务工具”的方向。筛选标准是：

1. 搜索词能拆成明确的用户任务；
2. 任务可以在单页 MVP 中真实完成；
3. 至少存在一种不依赖大规模流量的变现路径；
4. 数据或内容可以被结构化、更新和复用；
5. 风险不会让小团队在第一天就必须建设复杂后端或合规体系。

因此本次选择了 4 个互补方向：

| 站点目录 | 独立品牌 | 核心任务 | 主要搜索信号 | 类型 |
| --- | --- | --- | --- | --- |
| `apps/stackwise/` | Stackwise | 找到适合职业和任务的 AI 工具组合 | `best AI tools 2026`、`AI productivity tools` | 长期工具型 |
| `apps/switchboard/` | Switchboard | 比较下一部手机和配件兼容性 | `iPhone 18 price`、`release date`、`case`、`battery` | 发布窗口型 |
| `apps/costume-cartographer/` | Costume Cartographer | 根据人数、预算和时间规划装扮 | `Halloween 2026 costumes`、`couple costumes` | 季节型 |
| `apps/matchday-clock/` | Matchday Clock | 把赛事时间转换成当地可观看的时间 | `World Cup 2026 schedule`、`scores`、`today matches` | 事件型 |

## 2. 为什么选这 4 个

### 2.1 Stackwise：职业化 AI 工具筛选

**为什么选**

AI 工具搜索是长期需求，不依赖某一个节日或单次产品发布。前一轮联想词中出现了 `top`、`best`、`latest`、`new releases`、`free` 和 `productivity`，说明用户不仅想知道“有哪些工具”，还想比较和选择。

**相对泛 AI 目录的优势**

- 从职业和任务切入，而不是按“写作、图片、视频”做大而泛的列表；
- 结果解释“为什么适合”，而不是只展示工具名称；
- 可以加入预算、数据敏感度、集成方式和替代订阅等决策维度；
- 每个条目可以有核验日期，建立更新可信度；
- 推荐结果天然适合联盟链接、工作流模板和团队采购服务。

**当前 MVP 怎么验证**

选择 `E-commerce`、`Content & video`、`Recruiting`、`Real estate` 四类角色，再结合预算和任务筛选。核心指标是：

- 筛选完成率；
- `View fit` 点击率；
- 外链工具点击率；
- 用户是否保存或订阅更新；
- 用户提交纠错或推荐新工具的数量。

**后续壁垒**

壁垒不是工具数量，而是结构化的评测维度、职业工作流、更新记录和用户反馈数据。后续可以把条目从“目录”升级为“可执行的工作流模板”。

**风险**

工具价格、免费额度、隐私政策和 API 能力变化很快。上线前要把当前演示数据改成真实核验数据，并明确联盟关系。不能伪造用户评价或“最佳”结论。

### 2.2 Switchboard：手机购买与配件决策

**为什么选**

新手机发布窗口会集中产生 `release date`、`price`、`colors`、`specs`、`charger`、`case`、`battery life` 和型号对比等查询。此类用户已经接近购买决策，商业意图通常强于单纯新闻浏览。

**相对新闻搬运站的优势**

- 把规格转化为“我该买哪款”的判断；
- 结合已有手机、预算和优先级生成推荐；
- 增加充电器、保护壳和接口的兼容性检查；
- 比只做发布会资讯更接近联盟成交；
- 结构化数据可以扩展到 Pixel、Galaxy 和其他品牌。

**当前 MVP 怎么验证**

让用户选择当前手机、最重视的因素和预算，观察推荐结果是否被继续点击。核心指标是：

- 三个选择器的完成率；
- 推荐结果出现后的停留和点击；
- 配件兼容性模块的互动率；
- 型号对比页的自然搜索进入量；
- 联盟商品点击率。

**后续壁垒**

兼容性数据和跨品牌决策逻辑比单纯规格表更有价值。可以持续积累“旧设备 -> 新设备 -> 配件”的关系图，并按国家加入价格、保修和上市日期。

**风险**

当前页面使用的是产品化演示名称和示例数据，正式发布前必须根据真实官方资料改写。不能让用户误以为与 Apple 或任何手机厂商存在官方关系，不使用其 Logo，不把传闻写成已确认规格。

### 2.3 Costume Cartographer：Halloween 装扮规划

**为什么选**

Halloween 相关查询已经从节日名称细化到 `costumes`、`costume ideas`、`couple costumes`、`decorations`、`party costumes` 和 `events`。用户通常有明确约束：几个人、预算多少、是否 DIY、要不要吓人、能不能适合办公室或儿童活动。

**相对图片灵感站的优势**

- 根据约束生成可执行方案，而不是只展示图片；
- 同时处理人数、预算、天气和制作时间；
- 购物清单可以拆成“家里已有”和“需要购买”；
- 适合情侣、家庭、办公室和临时装扮等长尾搜索；
- 节后可以转向派对规划、生日主题和常青活动工具。

**当前 MVP 怎么验证**

测试个人、情侣、四人小组和亲子家庭四种入口，并观察：

- 用户是否完成选择；
- 方案是否触发二次修改；
- 购物清单点击率；
- 社交分享率；
- 节日前 14 天的自然访问增长。

**后续壁垒**

可以沉淀“人数 + 风格 + 时间 + 预算 + 天气”的方案数据库，进一步生成活动流程、装饰采购单和派对座位/游戏安排。

**风险**

节日流量有明显时间窗口，不能按全年常青项目估算。避免使用电影、游戏和品牌角色作为核心内容；儿童场景要加入安全提示，不收集不必要的儿童信息。

### 2.4 Matchday Clock：赛事时间转换

**为什么选**

赛事查询天然包含 `schedule`、`scores`、`bracket`、`standings`、`fixtures`、`schedule printable` 和不同城市/场馆。时区是一个具体且普遍的痛点：用户不只是要知道比赛存在，还要知道自己当地几点能看。

**相对普通赛程表的优势**

- 以用户所在地时间为第一信息；
- 能切换“全部比赛、我的关注、晚间可观看”；
- 适合导出日历、打印观赛表和组织群体观看；
- 可以为酒吧、办公室、球迷组织增加场景化模板；
- 赛事结束后仍可转为历史赛果、数据档案和下一届提醒。

**当前 MVP 怎么验证**

测试纽约、洛杉矶、伦敦、新加坡四个时区，观察：

- 时区切换使用率；
- 关注赛事筛选率；
- 赛事详情或保存动作；
- 打印/导出意愿；
- 用户来自哪个国家和时区。

**后续壁垒**

可靠的时区处理、日历导出、场馆交通和本地观看场景可以形成差异。相比实时比分本身，先把时间转换和观赛计划做好，技术和授权压力更可控。

**风险**

当前页面明确标注了 demo fixtures。接入真实比分前必须购买或获得授权的数据源，不能抓取未经许可的直播内容，也不能冒充赛事官方。赛事周期结束后要及时调整 SEO 文案，避免继续承诺“今天比赛”。

## 3. 四个站点的组合优势

### 3.1 时间风险分散

```text
Stackwise          长期更新需求
Switchboard        产品发布窗口
Costume Cartographer  节日季节需求
Matchday Clock     赛事事件需求
```

组合中既有常青方向，也有短周期方向。短周期站点可以快速验证分发和转化，长期站点负责积累内容、更新流程和稳定入口。

### 3.2 技术可以复用

四个站点都使用静态 HTML/CSS/JavaScript，能复用：

- 响应式布局和无框架发布；
- 表单选择器和实时结果面板；
- 埋点、SEO、robots 和 sitemap 模板；
- 发布到 Cloudflare Pages、Netlify 或 Vercel 的流程；
- Google Search Console 的验证与监控方法。

但它们没有共享品牌、文案、数据结论或页面内容，避免形成低质量复制站群。

### 3.3 变现方式互补

| 站点 | 第一种变现 | 第二种变现 |
| --- | --- | --- |
| Stackwise | SaaS 联盟 | 工作流模板、团队采购 |
| Switchboard | 配件联盟 | 设备比较导购 |
| Costume Cartographer | 服饰/装饰联盟 | 数字清单和活动模板 |
| Matchday Clock | 观赛场景赞助/联盟 | 日历导出和团体工具 |

## 4. 竞争优势不是“做得像”

这 4 个站点都参考了成熟网站的用户任务，但真正的竞争优势应放在以下方面：

- 首屏直接完成任务，而不是先看长篇营销文案；
- 输出结果能被保存、打印、分享或继续购买；
- 数据有来源、更新时间和限制说明；
- 只服务一个清晰的用户场景，避免泛目录；
- 每个实验提前设置核心动作和关闭条件；
- 观察真实反馈后再扩展页面和市场。

## 5. 建议测试顺序

1. **先测 Stackwise**：长期需求、数据可控、风险较低，适合验证更新和联盟模型。
2. **再测 Switchboard**：发布窗口商业意图强，适合快速观察点击和购买信号。
3. **同步测试 Costume Cartographer**：时间窗口短，但可以用小成本验证社交传播和节日联盟。
4. **最后接入 Matchday Clock 的真实数据**：先用 demo 验证时区和筛选交互，再决定是否购买数据授权。

## 6. 统一实验指标

每个站点至少使用以下事件命名，方便在组合看板中比较：

```text
page_view
primary_action_click
input_completed
result_generated
save_or_download
outbound_click
feedback_submitted
```

不要只比较页面浏览量。不同站点的成功动作不同：Stackwise 看工具点击，Switchboard 看导购点击，Costume Cartographer 看方案/清单互动，Matchday Clock 看时区筛选和保存。

## 7. 结论

本次 4 个站点的价值不在于“批量复制页面”，而在于形成一组可比较的需求实验：

- `Stackwise` 验证长期目录能否变成职业决策工具；
- `Switchboard` 验证发布热点能否承接购买意图；
- `Costume Cartographer` 验证季节热点能否转化为方案和联盟收入；
- `Matchday Clock` 验证事件数据能否转化为时区和观赛工具。

建议每个站点先只做一个主市场、一个主页面和一个核心动作，连续观察 14-30 天，再决定扩展内容、域名或独立仓库。

## 8. 本地预览路径

在项目根目录运行：

```bash
python3 -m http.server 4173 --directory site
```

然后分别打开：

- `http://localhost:4173/`：Calendar Forge；
- `http://localhost:4173/ai-tool-finder/`：Stackwise；
- `http://localhost:4173/device-decider/`：Switchboard；
- `http://localhost:4173/halloween-kit/`：Costume Cartographer；
- `http://localhost:4173/matchday-clock/`：Matchday Clock。

每个 `apps/<site-id>/` 目录都可以单独作为 Cloudflare Pages、Netlify 或 Vercel 的静态发布目录。正式发布时要为每个站点使用真实域名、真实数据源和独立的隐私/条款说明。
