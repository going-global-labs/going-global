# 自动化产品蓝图与 MVP 需求

## 1. 产品定位

### 1.1 产品名称（工作名）

Going Global：网站出海工作台。

### 1.2 要解决的问题

当前小团队做网站出海，资料散落在表格、翻译工具、代码仓库、广告平台和聊天记录中。成员不知道先做什么，也无法判断哪些页面已经完成、哪些风险没有处理、发布后的数据是否证明市场可行。

### 1.3 目标用户

第一阶段只服务以下人群：

- 有一个已经能在中国运行的网站或 SaaS 产品；
- 计划验证一个海外市场；
- 团队规模约 1 到 20 人；
- 没有专职国际化、SEO 或本地运营团队；
- 可以接受 AI 生成草稿，但希望保留人工审核。

暂不优先服务：大型跨国企业、强监管行业的全自动发布、复杂跨境仓储、电商 ERP 和纯翻译外包客户。

### 1.4 核心承诺

帮助用户把“我想做海外市场”转化为一条有证据、有负责人、有审批、有结果的执行流程。

### 1.5 北极星指标

**每个工作区每月完成并通过审核的有效海外市场发布任务数。**

“有效”至少满足：目标市场、语言、版本、负责人、审核记录和发布结果齐全。它比“生成了多少字”更能反映产品是否产生了真实价值。

## 2. 端到端用户流程

```text
创建工作区
  -> 填写产品和目标市场
  -> 扫描现有网站
  -> 生成市场机会报告和风险清单
  -> 选择首个市场
  -> 导入页面与术语
  -> AI 生成本地化草稿
  -> 人工审核/评论/批准
  -> 运行技术与 SEO 检查
  -> 生成发布包
  -> 连接网站或导出任务
  -> 发布后监测指标
  -> 根据反馈创建下一轮任务
```

## 3. MVP 功能范围

### P0：必须有

#### 3.1 工作区与项目

- 创建工作区、项目和目标市场；
- 记录语言、地区、货币、时区和项目状态；
- 角色：管理员、编辑、审核者、只读成员；
- 所有重要变更保留操作记录。

#### 3.2 网站扫描器

用户输入 URL 后，系统抓取允许访问的页面，识别：

- 页面标题、描述、正文、按钮、表单和图片 alt；
- 语言、链接、canonical、结构化数据和站点地图；
- 可能的硬编码文本；
- 需要翻译或人工确认的品牌词、产品名和技术词；
- 页面性能和基础可访问性问题。

输出页面清单和问题清单，不直接覆盖线上内容。

#### 3.3 市场启动向导

向导收集产品类别、目标用户、候选市场、价格、已有客户和限制条件，生成：

- 市场假设；
- 用户画像草稿；
- 竞品研究任务；
- 风险提示；
- 建议先做的页面和实验。

报告必须显示“依据”和“待验证假设”，不能把 AI 推测伪装成事实。

#### 3.4 本地化内容工作台

- 源文案、目标文案并排查看；
- AI 翻译/改写草稿；
- 术语库和风格指南；
- 变量、链接、HTML 标签保护；
- 评论、指派、审核、批准和退回；
- 版本对比与导出；
- 标记“机器初稿”“人工审校”“已发布”等状态。

#### 3.5 SEO 与发布前检查

至少检查：

- URL 结构、标题、描述、H1；
- canonical 与 `hreflang`；
- 站点地图和 robots；
- 页面内链、死链、图片 alt；
- 移动端和基础性能；
- 隐私、条款、退款和联系入口是否存在；
- 翻译变量是否损坏；
- 发布目标是否明确。

每条检查需要显示严重级别、定位、建议动作和是否阻塞发布。

#### 3.6 任务与发布包

- 按阶段生成任务；
- 任务有负责人、截止日期、依赖和验收条件；
- 支持导出 Markdown、CSV、JSON 或提交到 Git 分支；
- MVP 不直接接管用户生产环境，优先生成可审阅的发布包；
- 任何发布动作需要明确批准和可回滚版本。

#### 3.7 基础数据看板

显示：访客、来源、注册、激活、付费、退款、留存和错误。用户可以按市场、语言、页面和渠道筛选，并看到数据更新时间和采集范围。

#### 3.8 广告投放准备与归因

广告投放自动化不应从“自动花钱”开始，而应先保证投放可测量、可暂停、可复盘：

- 记录渠道、市场、广告系列、预算、关键词、素材、落地页和转化目标；
- 自动生成并校验 UTM 参数；
- 配置注册、激活、线索、购买和退款等转化事件；
- 显示花费、点击、转化、CAC、收入和 LTV 的统一口径；
- 设置每日/每周预算上限和异常告警；
- 在高花费、转化下降、追踪中断或合规检查失败时给出暂停建议；
- 支持导入 Google Ads 数据，但 MVP 不直接自动调整真实广告预算。

如果项目属于内容型网站，还应把广告变现和广告获客分开建模：

- Google Ads：记录广告花费、点击、转化和获客成本；
- Google AdSense 或其他广告网络：记录展示、点击、预估收入、填充率和页面收益；
- 不能把广告收入、产品订单收入和广告花费混在同一个“收入”指标里；
- 广告位实验必须观察对页面速度、核心转化和用户留存的影响。

### P1：验证后再做

- 一键同步 CMS 和翻译记忆库；
- 内容日历和批量 SEO 页面；
- Google Ads / 社交广告账户连接与只读报表；
- AdSense / 广告网络收入报表；
- 支付配置建议；
- 多语言客服知识库；
- 邮件和广告素材工作流；
- 多市场对比；
- 自动生成周报和实验建议。

### 明确不做（MVP）

- 自动替用户注册所有第三方账户；
- 自动生成并发布法律意见；
- 无人工审核的批量内容上线；
- 无预算上限和人工批准的自动投放、调价或扩量；
- 代替支付机构、税务机构或当地律师；
- 承诺“上线即有流量”或“保证排名”。

## 4. 关键数据模型

```text
Workspace
  └─ Project
      ├─ Market
      ├─ Site
      │   └─ Page
      │       └─ ContentItem
      ├─ GlossaryTerm
      ├─ LocalizationJob
      ├─ CheckRun / Finding
      ├─ Task / Approval
      ├─ Release
      └─ MetricSnapshot
```

### 核心实体说明

- **Workspace**：团队、成员、权限、计费和审计边界。
- **Project**：一个产品或网站的出海项目。
- **Market**：国家/地区、语言、货币、时区和合规状态。
- **Page**：被扫描或导入的页面及其版本。
- **ContentItem**：一个可翻译的文案单元，保留 key、上下文、变量和审核状态。
- **GlossaryTerm**：源词、目标词、禁用译法、备注和生效范围。
- **Finding**：扫描器发现的问题、严重性、证据、状态和负责人。
- **Release**：一次可追溯的发布包，包含内容版本、检查结果、批准人和回滚信息。
- **Campaign**：一个市场中的广告系列、预算、素材、关键词、落地页和转化目标。

## 5. 技术架构建议

第一版应优先使用简单、可观察、容易维护的架构：

```text
Web UI (Next.js / TypeScript)
        |
API / Auth / RBAC
        |
Domain Services
  - Project Service
  - Crawl Service
  - Localization Service
  - Quality Check Service
  - Release Service
        |
PostgreSQL ---- Object Storage
        |
Job Queue / Worker ---- AI Provider / CMS / Analytics
```

建议技术原则：

- 前端和后端使用严格类型；
- PostgreSQL 保存业务状态，对象存储保存抓取快照、导出包和大文件；
- 抓取、翻译、SEO 检查和报告生成使用异步任务；
- 每个任务有幂等 key、重试次数、超时和错误原因；
- AI 调用记录模型、提示版本、输入引用、输出和人工修改；
- 外部系统连接使用 OAuth 或加密密钥，不在日志中暴露 token；
- 广告平台连接默认使用最小权限，MVP 优先只读数据和转化诊断；
- 所有发布均先生成 preview，生产发布采用显式批准；
- 对用户网站的抓取遵守 robots、速率限制、权限和服务条款。

## 6. 自动化任务的统一状态机

建议所有长任务使用统一状态：

```text
PENDING -> RUNNING -> NEEDS_REVIEW -> APPROVED -> PUBLISHED
                    \-> FAILED -> RETRYING
                    \-> REJECTED -> EDITING
```

状态变更必须记录：操作者、时间、输入版本、输出版本、错误、审批意见和外部请求 ID。这样出现问题时，可以知道是抓取、模型、人工修改还是发布环节造成的。

## 7. AI 使用边界

### AI 可以做

- 根据上下文生成翻译初稿和多个标题候选；
- 从竞品页面中提取结构化信息；
- 发现术语不一致、可能缺少变量或表达不自然；
- 根据规则生成 SEO 检查建议；
- 把自然语言目标转换为任务清单；
- 对已有数据生成摘要，但要附带数据时间范围。

### AI 必须被约束

- 不得凭空生成市场规模、客户评价或合规结论；
- 不得擅自修改价格、法律条款和数据收集目的；
- 不得把未经审核的翻译自动推送到生产；
- 不得将用户私密内容发送给未授权的模型服务；
- 失败时必须保留原文并允许人工恢复。

## 8. MVP 验收标准

### 用户故事一：创建项目

作为没有出海经验的产品负责人，我想填写产品、目标市场和现有网站，以便得到一份有顺序的启动清单。

验收条件：

- 能创建项目并保存至少一个市场；
- 必填信息缺失时给出明确提示；
- 报告能区分事实、推测和待验证项；
- 每个建议至少有来源或生成依据。

### 用户故事二：导入并翻译页面

作为内容负责人，我想查看中英文对应内容并编辑术语，以便保证品牌表达一致。

验收条件：

- 能导入至少一种结构化格式；
- 变量、链接和 HTML 标签不会被破坏；
- 术语规则可以提示冲突；
- 翻译必须经过批准才能进入发布包；
- 可以查看版本差异和修改人。

### 用户故事三：发布前检查

作为工程负责人，我想在上线前运行检查，以便降低 SEO 和技术回归风险。

验收条件：

- 检查结果有严重级别和定位；
- 阻塞项存在时不能标记为可发布；
- 可以重新运行检查并比较结果；
- 发布包包含检查时间、版本和批准人。

### 用户故事四：追踪结果

作为创始人，我想按市场查看漏斗数据，以便判断是否继续投入。

验收条件：

- 能看到来源、访问、激活、付费和退款；
- 指标口径有说明；
- 数据异常或没有数据时有明确状态；
- 可以导出原始数据或报告。

## 9. 安全与合规基线

- 工作区数据隔离，服务端再次校验租户权限；
- 密钥加密保存，日志脱敏；
- 支持删除项目、导出数据和审计记录；
- 抓取前说明权限、频率和用途；
- 外部 AI 供应商需明确数据保留和训练政策；
- 对上传文件进行类型、大小、恶意内容和权限检查；
- 重要操作启用二次确认；
- 对发布动作保留不可篡改或至少可审计的记录；
- 默认不收集不必要的个人信息。

## 10. 产品成功的第一阶段信号

不要一开始用收入证明一切。先观察：

- 新用户是否能在 15 分钟内创建第一个项目；
- 是否能在一天内找到并修复最关键的本地化问题；
- AI 草稿被人工修改的比例是否逐步下降；
- 发布前检查发现的问题中，有多少被真正修复；
- 用户是否完成第二次市场或第二轮发布；
- 用户是否愿意用真实网站持续接入并反馈。
