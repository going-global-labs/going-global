# 90 天执行清单

这是一条适合小团队的保守路线。天数可以调整，但顺序建议保留。

## 第 1-7 天：建立基础认知

- 写清产品解决的问题和目标用户；
- 画出当前网站、注册、支付、客服和数据链路；
- 列出团队现有资源、预算和不能做的事情；
- 选出 3 个候选市场；
- 建立术语表和风险问题清单。

**验收**：能用一页纸说明“为谁、解决什么、先在哪个市场验证、为什么”。

## 第 8-21 天：验证市场和用户

- 完成候选市场对比；
- 访谈目标用户或阅读真实社区讨论；
- 研究 5 到 10 个竞品；
- 记录用户原话、购买阻力和常见问题；
- 选择一个主市场和一个核心场景；
- 写出停止条件，例如连续多少次测试仍没有激活或付费意愿。

**验收**：形成市场假设、ICP、竞争对比和首个实验设计。

## 第 22-35 天：设计 MVP 和本地化方案

- 确定首页、定价、注册、核心功能和帮助内容；
- 决定语言路由、币种、时区、客服和支付策略；
- 定义事件埋点和激活事件；
- 整理术语、风格指南和审核角色；
- 确定隐私、条款、退款、Cookie 和数据处理需要咨询的问题；
- 建立网站扫描、内容任务和发布检查的原型。

**验收**：每项工作都有负责人、状态和通过标准。

## 第 36-60 天：完成第一个市场版本

- 完成关键页面本地化；
- 实现语言切换或目标市场路由；
- 确认价格、支付、注册和邮件；
- 完成 SEO 基础配置；
- 接入分析和错误监控；
- 用真实目标用户做至少两轮可用性测试；
- 修复所有发布阻塞项。

**验收**：一个不熟悉产品的外部用户，可以在不依赖团队口头解释的情况下完成核心任务。

## 第 61-75 天：小范围发布

- 选择一到两个获客渠道；
- 准备内容、社区、合作或广告测试；
- 设置预算上限、频率和停止条件；
- 每天查看访问、激活、错误和反馈；
- 记录所有用户问题和页面流失点；
- 每周复盘一次假设，而不是只汇报流量。

**验收**：有真实用户进入、完成核心动作并留下可分析的反馈。

## 第 76-90 天：判断是否扩大

- 计算渠道成本、激活、付费和留存；
- 区分产品问题、表达问题、渠道问题和合规问题；
- 更新术语库、翻译记忆和任务模板；
- 决定继续深挖当前市场、调整定位，还是停止；
- 评估是否值得增加第二种语言或第二个市场；
- 把重复工作沉淀成自动化规则。

**验收**：形成一份有数据依据的“继续、调整或停止”决策，而不是凭感觉扩张。

## 每周复盘模板

```text
本周目标：
本周完成：
新增用户/合格线索/激活/付费：
最严重的三个问题：
我们认为的原因：
证据是什么：
下周实验：
成功标准：
停止条件：
需要人工或外部专家确认的事项：
```

## 最后的一句话

网站出海的本质不是把页面“搬到国外”，而是让一个特定市场的特定用户，在当地语境和业务规则下，顺利发现你、理解你、信任你、使用你，并且让团队能够用数据持续改进这条路径。自动化平台要做的，就是把这条路径变得清晰、可协作、可审计、可重复。
