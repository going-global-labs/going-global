# Going Global 生产架构与站点生命周期

> 本文是当前 `going-global-labs` 组织下孵化仓库的工程约定。

## 1. 当前定位

当前仓库是一个 **孵化 Monorepo**，用于低成本验证多个独立网站。它不是把所有网站作为一个产品发布，而是让多个应用共享工程管理，同时保持应用、域名、部署和数据边界。

```text
going-global/
├── apps/                    # 独立网站应用
│   ├── calendar-forge/
│   ├── stackwise/
│   ├── switchboard/
│   ├── costume-cartographer/
│   └── matchday-clock/
├── packages/                # 未来共享的 UI、SEO、埋点等包
├── services/                # 未来 API、worker、数据同步服务
├── config/sites.json        # 站点注册表
├── scripts/                 # 自动化校验和运维脚本
├── .github/workflows/       # 按应用隔离的 CI/CD
└── docs/                    # 产品、发布和运维文档
```

## 2. 四层边界

### 2.1 代码边界

每个网站放在独立的 `apps/<site-id>/` 目录。一个应用可以从静态 HTML 逐步演进为：

```text
apps/<site-id>/
├── web/          # 用户前台
├── admin/        # 管理后台（需要时再建）
├── api/          # 业务 API（需要时再建）
├── workers/      # 定时任务或异步任务（需要时再建）
├── public/
├── tests/
└── README.md
```

早期静态 MVP 可以暂时把入口放在目录根部，但一旦逻辑、测试或资源明显增加，就迁移到 `web/`，不要继续扩大单文件。

### 2.2 部署边界

每个生产网站对应自己的托管项目和 workflow：

```text
apps/calendar-forge/**
  -> deploy-calendar-forge.yml
  -> GitHub Pages project
  -> calendarforge.stream
```

其他网站不能因为共享仓库而自动更新 Calendar Forge。workflow 必须使用 `paths` 过滤，并把 artifact 指向自己的应用目录。

### 2.3 数据边界

不同网站不能直接共享业务数据库表、用户数据或业务 JSON。可以共享基础设施封装，但业务数据必须带有明确的应用归属：

```text
共享：认证 SDK、邮件客户端、埋点格式、数据库连接工具
隔离：用户、订单、推荐结果、内容、后台权限、生产密钥
```

需要数据库时，早期可以共享 PostgreSQL 实例但使用独立 schema；重要生产应用应迁移到独立数据库或独立项目。

### 2.4 域名边界

一个站点一个主域名，一个 sitemap，一个 Search Console 资源：

```text
Calendar Forge -> calendarforge.stream -> calendarforge.stream/sitemap.xml
Stackwise      -> 待定              -> 待定
```

不要把实验站点写入 Calendar Forge 的 sitemap，也不要让多个网站共用一个 canonical。

## 3. 站点状态

站点状态记录在 `config/sites.json`：

```text
idea -> research -> experiment -> staging -> live -> growing
                                      -> paused -> archived
```

- `idea`：只有选题卡；
- `research`：研究搜索、竞品和用户任务；
- `experiment`：有 MVP，但没有生产域名；
- `staging`：准备部署，正在做真实数据、合规和可用性检查；
- `live`：绑定域名并可被公众访问；
- `growing`：有持续核心动作或收入，值得投入；
- `paused`：暂时停止投放和新增功能；
- `archived`：停止维护，但保留代码和实验记录。

状态升级必须有证据。没有核心动作、收入、反馈或稳定访问时，不因为页面已经完成就标记为 `live` 或 `growing`。

## 4. 共享代码规则

只有满足以下条件，才把代码放入 `packages/`：

1. 至少两个应用确实需要；
2. API 和行为可以稳定描述；
3. 共享不会引入业务耦合；
4. 有独立测试或使用示例。

推荐未来的包：

```text
packages/ui           # 通用无业务 UI
packages/seo          # title、canonical、sitemap 工具
packages/analytics    # 统一事件名和埋点客户端
packages/config       # 环境变量和运行时配置校验
```

不要因为两个页面暂时长得像，就马上抽象。抽象错误比重复几行代码更难维护。

## 5. 环境与密钥

每个生产应用至少区分：

```text
local -> staging -> production
```

各环境的数据库、OAuth、支付、分析 ID 和 API Key 不得混用。密钥只放在 GitHub Actions Secrets、托管平台 Environment Variables 或专门的 Secrets Manager，不提交到仓库。

建议的 GitHub Environment：

```text
github-pages-calendar-forge
calendar-forge-staging
calendar-forge-production
```

生产部署可以增加 required reviewers，避免任何普通分支直接修改生产配置。

## 6. CI/CD 约定

每个应用的 workflow 应包含：

1. checkout；
2. 安装并锁定依赖；
3. 运行格式、类型、单元测试和站点清单校验；
4. 构建该应用自己的 artifact；
5. 部署到该应用的托管项目；
6. 输出部署 URL 和版本信息。

当前静态阶段至少执行：

```bash
npm run validate
```

未来使用 Monorepo 工具后，再根据受影响的 app 做增量构建，不让所有网站无条件重建。

## 7. 什么时候拆成独立仓库

满足任意两项时，可以把应用从孵化 Monorepo 迁移到组织下的独立仓库：

- 有稳定生产域名；
- 有后台、API 或数据库；
- 有独立负责人或外部合作方；
- 需要独立发布节奏；
- 需要独立权限和 Secrets；
- 产生稳定收入或持续自然流量；
- 未来可能出售、转让或单独成立团队。

迁移后的形态：

```text
going-global-labs/
├── going-global-incubator
├── calendar-forge
├── stackwise
└── shared-platform
```

迁移时保留 Git 历史、域名、Search Console、分析数据和实验记录，不直接复制粘贴后丢失版本关系。

## 8. 当前执行结论

当前仓库继续承担孵化职责；Calendar Forge 已绑定 `calendarforge.stream` 并完成 GitHub Pages HTTPS，状态进入 `live`，拥有独立 workflow；其余 4 个网站保持实验状态。等任一实验达到升级条件，再迁移为组织下的独立生产仓库。
